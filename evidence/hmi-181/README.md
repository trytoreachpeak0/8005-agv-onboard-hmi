# onboard-hmi#181 红绿证据

hmi#176 的恢复入口写入守卫（`tests/SQCD.Agv.UnitTests/RecoveryEntryWriteSiteArchitectureTests.cs`）守的是：九个恢复入口属性
只能经两种写法写入——右边整个是一次 `AllowRecoveryEntry(...)`，或者落在同一个成员里一道有效的
`RecoveryEntriesBlockedByFatalFault` early return 之后。第三条写入路径出现就红，因为严重安全故障锁存期间那条路径会把入口放回来，
而其中三个入口按下去会真的开仓门。

那道守卫原来逐行用正则读 `MainViewModel.cs`：按「行里第一个 `//`」剥注释，按缩进四格的 `}`／`;` 切成员，逐行找写入、逐行分类。
hmi#162 的五轮审查证实这种读法会一再漏掉跨行、字符串里的 `//`、表达式体成员等写法，最后在测试里建了一个最小 C# 词法层才收住。
本票把那层抽成两个守卫共用的 `tests/SQCD.Agv.UnitTests/CSharpSourceLexer.cs`，让 #176 的守卫改用它。

本目录是**定向核对之后**的版本。第一轮审查找到一个本票引入的回退（S1）和一个基分支就有的漏洞（S2），都已修；定向核对又找到一处
同机理的缺口（同一语句内的第二次写），基分支同样看不见，按规矩不追、如实写进限度并钉住。见下面「审查改了什么」。

## 改了什么

- **共用辅助，不复制**：`CSharpSourceLexer`（词法层 `Lex`、成员切分 `MemberSpans`、成员名 `NameOf`、续行记号正则）从
  `RecoveryMarkerPersistenceArchitectureTests.cs` 原样挪出，那个文件净删 469 行、改为引用它。hmi#162 的九条守卫全绿。
- **#176 的守卫改用它**：去注释改用词法层的代码视图（注释与字面量抹成等长空白，行号不变），成员切分改用 `MemberSpans`。
- **跨行不是一条新规则**（票面「不追加新的禁用写法清单，统一判据」）：原有的写入形状（简单／复合赋值、解构、`ref`／`out`）
  改为对整个成员的代码文本匹配，正则里的 `\s*` 本来就跨得过换行；命中位置再折回行号。
- **分类单位是语句，不是行**（审查之后，`7137afd` 起）：一次写归到它所在的那条语句——从上一个 `;`、`{` 或 `}` 之后到下一个 `;`——
  一条语句对一个入口判一次。守卫块内「只许写 false」数的也是这条语句。这取代了第一版的「从名字所在行的行首数到 `;`」，
  那个口径正是 S1 的来源。不同语句各自判定；**同一语句内对同一入口的多次写只判一次，第一次的合规形状会掩护后面的**（见限度）。
  语句边界是按这三个字符往回找的，不是语法分析。
- **扫描器自检加两项**：视图模型里每个成员都切得出名字，且没有成员以续行记号开头（hmi#162 第四轮复审：深度与命名两项拦不住深度 1 上的错切）。
- **合成反例**：本票补逐行读法看不见的四种（跨行赋值、字符串里的 `//`、换行的表达式体属性、守卫块里跨行打开入口），审查后再补六种
  （守卫块里跨行的 `ref`、解构两种、`out`，同一行第二次写的普通版与 setter 版），另有合规例（守卫块里跨行写 false）。

真实源码上的写入点条数（25）与写入成员（三个）前后都没变。产品代码没有改。

## 票面第 2 项的三种写法：修前与修后

在真实 `MainViewModel.cs` 上注入，跑 `RecoveryEntryWriteSiteArchitectureTests`（5 条）。预期都在跑之前写进每份 `.txt` 开头；
`.patch` 对当时的 HEAD 生成并通过 `git apply --check`；每次注入后按字节备份还原，blob 与 HEAD 一致。`before/` 在基分支 `4cd715e` 上跑，
`after/` 在 `3808209`（定向核对之后）上重跑；两者之间 `MainViewModel.cs` 没有变，所以两组 patch 相同。

| 写法 | 修前（`before/`） | 修后（`after/`） |
| --- | --- | --- |
| 1 跨行赋值：新方法里 `CanRequestLoadCompensation` 换行 `= true;` | **5 条全绿**：两行各自都不像一次写，条数不变，连「扫描器还睁着眼」也不响 | 红 2 条：写入守卫 + 扫描器自检（条数 26、多出写入成员 `ReopenCompensation`） |
| 2 字符串里的 `//`：`string link = "onboard://recovery"; CanRequestLoadCompensation = link.Length > 0;` | **5 条全绿**：后半行连同写入被当成注释剥掉 | 红 2 条，同上 |
| 3 表达式体属性写入：`private bool ReopenCompensation =>` 换行 `CanRequestLoadCompensation = true;` | **已经红 2 条**，违规写入记在并进去的 `RefreshWireToGateInputStateCore` 名下 | 红 2 条，违规写入记在 `ReopenCompensation` 自己名下 |

**第 3 种与票面前提不符。** 票面说三种在当前守卫下都为绿；实测第 3 种修前就是红的。三种放法都试过，都红，只是基分支上的成员名
取决于放在哪里：放在写入成员前 → `RefreshWireToGateInputStateCore`，放在写入成员后 → `OnVehicleSafetySignalChanged`，写成单行 →
`(unnamed)`。原因是 #176 的守卫没有闭包，逐个写入点判定：表达式体成员切错、并进相邻成员，写入仍落在某个成员里，既不是
`AllowRecoveryEntry` 包着的写，也不在守卫之后，于是判违规。hmi#162 那边同名的问题是错切让闭包跟不进无名成员，这里没有闭包，
那个失效形状不存在。

**调度据此把完成标准改为**：跨行赋值、字符串里的 `//` 两类「修前绿、修后红」；表达式体写入一类「两边都红」，作回归钉在合成自检里，
断言它的成员名是它自己（票上已有更正评论）。

## 审查改了什么

**S1（本票第一版引入的回退）**：守卫块里跨行的 `ref`／`out`／解构写入被判合规。第一版的计数文本从入口名字所在行的**行首**截起，
`SetProperty(ref` 换行 `_canX, …)` 里的 `ref`、`(_,` 换行 `CanX) = …` 里的 `(` 都在上一行、被截在外面，于是数出 0 次写、0 次 false，
两边相等而判合规。基分支上这四种反而会让条数那条红（逐行读看不见这次写，而它顶掉了原来那句 `= false`），所以是回退。

**S2（基分支就有）**：同一行上的第二次写被吞掉。`CanX = AllowRecoveryEntry(...); CanX |= HasPhysicallyUnknownSlots;`，以及 setter 里
`SetProperty(ref _x, value); _x |= …;`，按（行，入口）分类时这一行只要有一次合规写，整行放行。

两个修法二选一时选了**把分类单位从行改成语句**，而不是把 S2 写进限度：语句的 `;` 边界现成就有，改动集中在 `Scan` 与 `Classify`，
而且同一处改动把 S1 一起修掉了——语句从上一个 `;`／`{`／`}` 之后算起，上一行的 `ref`、`(` 自然在里面。

**M1**：限度表、合成例注释、本 README 与 PR 正文按修后的实际能力改写，写明起点（`7137afd`）；基分支上三种放法的成员名如实写出。

**定向核对（`3808209`）**：同一语句内对同一入口的第二次写被第一次的合规形状掩护——`private set => _ = SetProperty(ref _x, value) | (_x |= y);`、
`… | SetProperty(ref _x, value || y);`、`AllowRecoveryEntry(… Task.Run(() => CanX |= y) …)`。基分支同样看不见，不是本票引入。
按扫描护栏「第二轮仍有绕法就停」**不追**：限度文字从「同一行上的几次写各自判定」改为如实的「同一语句内只判一次」，补上
「`AllowRecoveryEntry(...)` 实参里的 lambda」这一类；第一种钉成合成自检里「看不见」的一例（`AssertCompliant`，失败时说明扫描器变强了）。
合成例与注入里的 `Open(out …)` 在真实文件上编译不过（没有 `Open` 方法），换成 `_ = bool.TryParse("true", out …)`，
所有注入都逐个放进真实文件编译过（`0 Error(s)`），`review/` 三个版本重跑，结论不变。还原一律用不带 `-p` 的 `cp`，
修改时间会更新，MSBuild 不会跳过重编。

## 这道守卫仍然看不见的写法（登记在 `GuardLimits`）

- 经反射或 XAML 双向绑定写入；在别的文件里写（今天九个属性都是 `private set`、类不是 partial，那是状态不是保证）。
- 写另一个实例的入口（`other.CanX = true`）：写入形状排除了点号前缀。
- 守卫之后把写入放进 lambda 或本地函数延迟执行：判合规（合成例按当前结果钉着）。写在 `AllowRecoveryEntry(...)` 实参里的 lambda 同样判合规。
  「early return 之后」按行号与缩进近似，不是控制流分析。
- 同一语句内对同一入口的多次写只判一次，第一次的合规形状会掩护后面的（合成例钉着 setter 版；基分支同样看不见）。
- 九个之外的新入口。
- 语句边界按 `;`／`{`／`}` 往回找，不是语法分析。
- 词法层自己的限度：同一行两个成员共用这一行；用转义写的标识符认不出；原始字符串拒读（大声失败）。

这是防回归护栏，不是证明：它认的是已经想到的写法形状。按票面，第二轮复审仍有绕法就停下，统一判据并收窄声称，不继续加禁用写法。
